> 日期：2026-08-08
> 目的：从"常规爬虫流程"视角拆解本项目采集链路，定位当前吞吐瓶颈（木桶效应）卡在哪，为后续优化提供依据。

## 1. 常规爬虫的 8 个环节（理论框架）

爬虫采集本质是「**生成待办 → 逐个抓取 → 解析产物 → 落库**」，可拆成 8 环节：

```
① 任务生成     确定爬什么: 关键词×城市×页数 笛卡尔积 / URL 列表
② 请求构造     URL + headers + params + 代理 + 指纹模拟 (TLS/HTTP2)
③ 本地请求     发出 HTTP 请求 (走网络)
④ 服务端校验   服务器鉴权/风控: 指纹放行 or 挑战 or 验证码
⑤ 返回数据     HTML / JSON / 或 验证码页 / 错误页
⑥ 解析         提取目标字段 (ID / 详情字段)
⑦ 去重 + 入队   ID → 任务队列 (SADD 去重)
⑧ 队列调度     并发 + 限速 + 失败重试 + 冷却
⑨ 入库         写数据库 (upsert 幂等)
```

> **概念纠正**：队列里装的不是「数据」，是「下一步要做的任务」（通常是轻量 ID）。
> 数据是 worker 消费任务、发请求拿到的，**直接入库**，不再过队列。

## 2. 智联项目实际链路（对照实现）

智联采集是**两阶段流水线**：搜索产 ID → 详情拉数据。全链路 9 环节逐项对照：

```
┌─ produce ①任务生成 ─────────────────────────────────────────────┐
│  collect.py --produce                                           │
│  → 城市×关键词 笛卡尔积 → search 队列 keyword:任务 (自动翻页)     │
│  → --companies → company:任务 (公司名补采)                        │
└──────────────────────────────┬─────────────────────────────────┘
                               ▼
┌─ consume: 搜索 worker (search 队列, 桶 20/s) ───────────────────┐
│ ②请求构造  _search_page_async: sou.zhaopin.com/?jl=&kw=&p=       │
│             curl_cffi chrome 指纹 (走本地代理 fake-ip)            │
│ ③本地请求  发送, 热连接 ~547ms/请求                               │
│ ④服务端校验 EdgeOne: TLS/HTTP2 指纹放行; 否则 JS Challenge/验证码  │
│ ⑤返回数据  SSR HTML (__INITIAL_STATE__, 20 条/页, ~340KB)         │
│ ⑥解析      extract_initial_state → positionList → number/company │
│ ⑦去重+入队 岗位号 → position 队列 (SADD); 新公司号 → company 任务   │
│            公司号+名 → companies 表 (upsert_company_mini)         │
└──────────────────────────────┬─────────────────────────────────┘
                               ▼
┌─ consume: 详情 worker (position 队列, 桶 80/s) ─────────────────┐
│ ②-⑤  fetch_position_detail_v2_async:                            │
│       fe-api detailv2 JSON, 热连接 ~211ms/请求, 响应 7KB          │
│ ⑥解析      parse_position_detail_v2 → 67 字段职位 + 22 字段公司    │
│ ⑧队列调度  双队列 + 双桶限速 + 崩溃恢复 + 重试3次 (见 §3)          │
│ ⑨入库      upsert_position (positions) + upsert_company          │
└──────────────────────────────┬─────────────────────────────────┘
                               ▼
                         PostgreSQL (positions / companies / runs)
```

**关键点**：
- 搜索和详情**各走一遍**「请求→校验→返回→解析」；
- 搜索的解析产物是**任务**（ID 入队）；详情的解析产物是**数据**（直接入库）；
- 公司补采（阶段二）是 keyword 搜索发现公司号 → `company:任务` → 按公司名再搜全国。

## 3. 每环节耗时实测（2026-08-08）

### 3.1 代理 vs 直连 网络分段（冷连接，各 5 次均值，单位 ms）

初始测试走本地代理（Clash fake-ip，DNS 解析到 198.18.0.x）；关梯子后直连
（真实 IP `117.69.71.80` 等，且两域名解析到**同一组服务器**）。

| 环节 | 搜索(代理) | 搜索(直连) | 详情(代理) | 详情(直连) |
|---|---|---|---|---|
| DNS | 4 | 6 | 1 | 2 |
| TCP 连接 | 9 | 43 | 2 | 21 |
| TLS 握手 | 85 | 39 | 37 | 19 |
| **TTFB（服务端处理）** | **490** | **446** | **203** | **197** |
| 下载 | 22 | 23 | 0.2 | 0.1 |
| **冷连接总计** | **611** | **558** | **244** | **239** |

> 直连对详情无影响（TTFB 恒定 ~200ms）；对搜索略快（TLS 少一跳隧道）。
> 关键：TTFB 两个模式基本一致 → 延迟与服务端渲染成本强相关，**与网络链路无关**。

### 3.2 热连接（keep-alive 复用，贴近采集稳态）

| | 代理 | 直连 |
|---|---|---|
| 搜索 | ~547 ms | **~449 ms** |
| 详情 | ~211 ms | **~203 ms** |

> 采集的 AsyncSession 复用 TCP，稳态即热连接值。

### 3.3 本地处理耗时（每请求）

| 环节 | 耗时 | 说明 |
|---|---|---|
| 搜索 SSR 解析 | 3-6 ms | 正则 + JSON 解析 20 条/页 |
| 详情 JSON 解析 | ~1 ms | 字段映射 |
| PG 写（upsert_position） | 1-2 ms | 单条 INSERT，连接池并发 |
| PG 写（upsert_company_mini） | ~1 ms/条 | 搜索 worker 每页 20 条串行 |
| Redis 入队/出队 | 0.5-1 ms | 本地，SADD+RPUSH/BLPOP |

### 3.4 网络健康对照实验（证明延迟 = 服务端计算，非本机网络）

关梯子直连下，本机到智联服务器的网络链路逐项体检（2026-08-08）：

| 检测项 | 结果 | 判定 |
|---|---|---|
| ping 智联真实 IP | RTT **12-18ms** | ✅ 链路极快 |
| TCP 连接 / 网卡 | 65 连接无异常（抖音/豆包/PyCharm 等分摊）/ 千兆 I219-V | ✅ 无瓶颈 |
| 静态资源 TTFB（独立 CDN `common-bucket.zhaopin.cn`）| **63ms** | ✅ 接近纯 RTT 基线 |
| 智联首页 SSR TTFB | 143-165ms | 轻量页正常 |
| 详情 detailv2 TTFB | 197ms | 与首页同级 |
| **搜索页 sou SSR TTFB** | **446-561ms** | 服务端重活 |

**归因公式**：`TTFB ≈ RTT(请求上行 + 响应首包 ≈ 2×12ms) + 服务端处理时间`。

- 静态资源 63ms ≈ 纯链路 RTT 基线（服务端 ~0ms）
- 首页 143ms ≈ 链路 + 轻量渲染
- 搜索页 446-561ms = 链路 + **~420ms+ 服务端 SSR 聚合渲染**（聚合职位/排序/推荐/广告）
- **结论**：本机网络是干净的，sou 搜索页慢 100% 是智联服务端渲染成本，客户端无法单请求优化，只能靠并发摊薄。

## 4. 木桶效应分析（瓶颈在哪）

### 4.1 每环节产能上限对比

| 环节 | 产能上限 | 约束性质 | 是否瓶颈 |
|---|---|---|---|
| 搜索请求 | **20/s**（桶设定） | 风控主动限速（实测 33/s 安全，留余量）| ❌ 安全阀，非木桶 |
| 详情请求 | **~70/s**（服务器单 IP 软限）| **服务器端硬限制**（并发 10/20/30/40 实测一致）| ✅ **主木桶** |
| 搜索→详情放大 | 20/s × 20 条/页 = 400 任务/s | 命中率相关的理论值 | 富余，不拖累 |
| PG 入库 | 1000+/s | 本地 1-2ms/条，20 连接池 | ❌ |
| Redis 队列 | 数千/s | 本地 0.5ms/次 | ❌ |
| 本地解析 | 数百/s | 3-6ms/次 | ❌ |

### 4.2 结论：主木桶 = 详情 detailv2 单 IP 服务器软限 ~70/s

**整条流水线的最终吞吐 = 详情速率 = ~70 岗位/秒**。理由：

1. 详情是唯一受**服务器端硬限制**的环节（单 IP 软限，与客户端并发、桶速无关，实测并发 10/20/30/40 均为 ~70/s）。
2. 上游搜索产能（理论 400 任务/s）远超详情消化（70/s），只要搜索命中率 > ~17.5%（每页 >3.5 条）详情就持续满负荷 → **系统吞吐恒 = 70/s**。
3. 本地环节（解析/PG/Redis）产能全部高一个量级，不是瓶颈。

**当前吞吐量级**：70/s × 3600 ≈ **25 万岗位/小时**；100 万岗位 ≈ **4 小时**（单 IP）。对业务目标（百万级）足够，但速率被服务器钉死在单 IP 上限。

### 4.3 次级约束（不是木桶，但要理解）

- **搜索 20/s 是风控驱动的刻意保守**：搜索接口 IP 信誉敏感，实测 33/s 安全，配置 20/s 留余量。搜索产能远超详情消耗，降搜索桶不影响最终吞吐（详情才是瓶颈）。
- **搜索单任务自动翻页**：一个 keyword 任务翻完所有页（如 100 页 = 100 次搜索请求 ≈ 55s），多个任务并行抢全局 20/s 桶。若关键词命中页多，翻页时间长，但**不阻塞详情**（详情队列持续有货）。
- **公司名补采（阶段二）**：每公司 1 个搜索任务（通常翻 1-3 页），共享 search 桶。5000 公司 × 2 页 ≈ 1 万请求 ÷ 20/s ≈ 8 分钟，非瓶颈；产出岗位仍走详情 70/s。

### 4.4 为什么搜索和详情延迟不同（§3 归因）

差异 367ms 里，**287ms（78%）在 TTFB** = 服务端渲染成本差异：搜索页是 SSR 整页渲染（服务端聚合+拼 HTML 340KB），详情是轻量 JSON API（查单条返回 7KB）。这是**服务端处理性质差异，客户端无法单请求优化**，只能靠并发摊薄。其余为 TLS 握手（代理路由）+ 下载体积。

## 5. 提升吞吐的方向（按杠杆从大到小）

| 方向 | 杠杆 | 说明 |
|---|---|---|
| **多 IP 扩展** | **×N**（每 IP ~70/s 线性叠加）| 唯一能直接突破主木桶的手段：多机 / 代理池分布式采集（当前单机单 IP）。每加一个 IP 的稳定 IP 信誉，详情吞吐 +70/s |
| 提高搜索命中率 | 让详情队列吃满 | 命中率过低（<17.5%）时详情饿着，吞吐 <70/s。优化关键词组合、城市覆盖 |
| 公司补采去重 | 减少重复搜索 | 同名公司、重复命中公司号由 `seen` 去重；公司号去重已做（SADD） |
| 断点续采（resume） | 防重跑浪费 | 生产走 Redis 队列天然幂等（PK upsert）；单机 Pipeline 已有 resume |
| 桶/并发微调 | 无效 | 详情桶 80/s > 软限 70/s，加并发实测无提升 → 不值得投入 |

**结论一句话**：木桶卡在**详情接口的单 IP 服务器软限 ~70/s**；本地全部环节富余；搜索 20/s 是风控安全阀不是瓶颈；**想提速唯一有效杠杆是多 IP 并行**，否则 100 万岗位 ≈ 4 小时是当前硬上限。

## 7. 日志观测体系（分环节耗时统计）

采集器内置一套「实时 4 行 + 结束总结表」的延迟观测（2026-08-08 新增，
`utils/latency_stats.py`），用于运行中 + 跑完后定位木桶。

### 实时（进度显示器第 4 行，每秒刷新累计均值）

```
[延迟] 搜索 449ms(TTFB 446) | 详情 211ms(TTFB 197) | 解析 1.2ms | 入库 1.8ms
```

### 结束总结（每 worker 收敛后打印一次，终端 + 日志同步）

```
  环节      样本  均值    p50     p95     max       (TTFB)
  搜索网络     128   449ms   432ms   511ms   585ms  (446ms)
  详情网络     812   211ms   208ms   262ms   300ms  (197ms)
  搜索解析     128     4ms     4ms     5ms     6ms  -
  详情解析     812     1ms     1ms     1ms     2ms  -
  详情入库     812     2ms     2ms     2ms     3ms  -
  搜索入库    2560     1ms     1ms     2ms     2ms  -
  冷却等待       2  3000ms  3000ms  3000ms  3000ms  -
```

主进程最后输出 `采集完成: 总耗时 00:12:34, ...`。

### 指标选择依据（为什么只采这些）

| 指标 | 采集 | 依据 |
|---|---|---|
| **TTFB**（STARTTRANSFER）| ✅ 网络核心 | = 服务端处理 + 1 RTT，单请求延迟核心，决定并发需求 |
| **总耗时**（TOTAL）| ✅ 网络核心 | 端到端，对应吞吐 |
| DNS / TCP / TLS | ❌ 不采 | keep-alive 稳态每连接一次 ≈ 0；链路属性非采集可控；采了污染统计 |
| 解析 / DB 写 / 冷却 | ✅ 本地核心 | 每次请求发生，证明木桶在服务端还是本地 |
| 本地解密 / 签名 | ❌ 不采 | detailv2 纯 JSON 无挑战、参数非签名，本地零计算 |

**实现**：`AsyncZhilianClient` 的 session 加 `curl_infos=[STARTTRANSFER_TIME, TOTAL_TIME]`
（curl_cffi 原生，requests 层行为不变），每个响应自动携带分段；本地环节用
`time.perf_counter()` 埋点。**不迁移底层 Curl API**，无生产风险，0 额外请求。

**口径**：p50 看典型、p95 看尾部最坏常态、max 抓异常、均值看整体——单看均值会被
极端值骗。多 worker 各自打印带 worker id 的表；实时行仅 worker0 显示（各 worker 逻辑
相同，统计代表整体）。

### 已知限制（代码审查 2026-08-08 确认，非阻断）

- **限速等待 / 重试退避 / 失败请求不计入**任何 stage → 网络统计系统性乐观（墙钟时间 >
  各 stage 之和，波动越大缺口越大）。失败尝试不记样本。
- **keyword/company 的 Redis 入队不计入**本地耗时（`enqueue_many`/`is_failed` 每页
  100-300ms 未计量，仅 `db_search` 的 upsert 部分被计）。
- **重定向链只采最后一跳**（curl TOTAL/STARTTRANSFER 反映末次 transfer）；详情
  `resp.json()` 解码与 `_trim_raw_json` 未计量（本地 CPU 成本漏计）。
- **样本有界窗口** `MAX_SAMPLES=50000`/stage（deque）——超出只保留最近样本，百万级
  任务下内存可控（~5MB/worker 级），但长期运行早期样本被丢弃。
- 冷却等待在并发请求下每请求各记一条（count 被并发数放大，均值仍准）。
